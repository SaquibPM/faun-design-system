## When to use

- For three or more related actions on one object: table actions, text formatting, chart tools.
- When tabbing through every button would be tedious: a toolbar is one tab stop, and arrow keys move inside it.

## When not to use

- For one or two actions. Use plain [Buttons](/components/button).
- For choosing between exclusive options. Use a [Segmented control](/components/segmented-control).
- For a set of buttons that act as one control. Use [Button group](/components/button-group).
- For a long list of commands. Use a [Menu](/components/menu).

## Writing

Every control needs a name: it is the tooltip and what a screen reader says. Name the action, not the icon: “Export”, not “Download arrow”.

## Anatomy

A bordered strip with ghost icon buttons (28px by default), separators between groups, and a trailing More button when folding. A pressed toggle is tinted and carries `aria-pressed`.

## Notes

- `label` is required and names the toolbar.
- A `ToolbarButton` with `pressed` is a toggle; give it `onPressedChange`. Without it the button takes `onClick`.
- Use `showLabel` for a text button; do not mix with icon-only controls in one toolbar.
- Controls report themselves to the toolbar, so any nesting depth works as long as they render inside it.
- Overflow measures each control once while it is visible, so fixed-width controls work best.

## Screen readers

- A `toolbar` with a name and orientation. Toggles are announced as pressed or not pressed. Disabled controls are skipped by the arrow keys.
- Controls folded into the menu keep their names; toggles become checked menu items.

## Visual

- Icon controls meet the minimum target size. Focus shows the standard ring. Pressed state is a tint and is also announced as a state, so it does not rely on colour.
