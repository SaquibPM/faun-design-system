## When to use

- Around every form control that is not already a TextField: selects, comboboxes, date pickers, sliders.
- Use `Fieldset` to group related fields under one legend.

## When not to use

- Around a checkbox or switch that has its own label and description.
- To lay out a form. Use Stack, Inline or Grid.

## Anatomy

Label row (label, required mark or Optional, optional action), the control, help text, and error with an icon. Help text and error use the caption and body-small roles.

## States

Default, required (asterisk, hidden from screen readers because the control carries `aria-required`), invalid (danger text and icon), warn (amber text and icon), read-only (flat nested surface), skeleton (shimmering placeholder) and disabled. All controls draw the same states from the same `data-invalid`, `data-warn`, `data-readonly` and `data-skeleton` attributes.

## Notes

- Controls built on `useFieldControl` (Input, Select, Combobox and the other form controls) pick up the id, `aria-describedby`, `aria-invalid`, required and disabled from the Field.
- Use `hideLabel` only when the purpose is obvious from context. The label stays available to screen readers.
- Pass `controlId` when you need a stable id.
- `warn`, `readOnly` and `skeleton` apply to every control inside the Field. Skeleton keeps the label for screen readers, disables the control and hides the description and messages.

</Section>

<Section tab="accessibility">

## Keyboard

Field is not interactive. Focus goes to the control.

## Screen readers

- The label is associated with the control. Description and error are listed in `aria-describedby`, and the error is announced with `role="alert"`. A warning uses `role="status"`, so it is read politely.

## Visual

- Error and warning text meet 4.5:1 and always have an icon, so neither relies on colour.
- Read-only fields stay focusable and keep full-contrast text; disabled fields do not.
